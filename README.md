# 下班换个活法 · 社畜换装小游戏

一个以打工日常为主题的网页换装小游戏：白天搭配通勤装备，应对工作事件；晚上换上自己喜欢的衣服，恢复精神值，解锁吐槽剧情。

**项目状态：筹备中。** 本文记录首版范围、技术设计与开发协作计划，尚不代表已实现功能。目前没有可运行版本或试玩地址；安装、启动和部署说明将在代码落地后补充。

## 项目目标

做一个手机和桌面浏览器都能玩的轻量小游戏，让服装搭配同时影响角色外观、属性和剧情。先完成小规模、可验证的游戏循环，再通过配置增加衣服和事件。

## 玩法与首版范围

一轮游戏由“白天选装 → 工作事件 → 晚上换装 → 休息结算”组成。

- **白天：** 穿搭影响打工效率和老板好感，工作事件根据属性与选择给出不同结果。
- **晚上：** 换装与休闲事件影响精神值，触发不同的吐槽对白。
- **结算：** 保存当日结果、已解锁服装和剧情进度，进入下一天。

首版计划包含：

| 内容 | 范围 |
| --- | --- |
| 角色 | 1 个固定姿势的角色底模，具体形象待定 |
| 服装 | 加班套装、周末逃离都市风、夜间放松风，共 3 套可拆分搭配的服装 |
| 槽位 | 头发、上衣、下装、鞋子、配饰 |
| 属性 | 打工效率、老板好感、精神值；具体数值待试玩调整 |
| 事件 | 5 个事件，覆盖工作与休闲场景 |
| 存档 | 浏览器本地保存，支持刷新后恢复 |
| 平台 | 桌面与手机浏览器 |

事件示例包括临时改需求、临下班开会、客户沟通、周末出游和夜间放松。首版不包含账号系统、云存档、付费商城和多人玩法。

## 技术方案

以下为拟采用的技术栈，具体依赖版本将在初始化项目时确定。

| 技术 | 用途 |
| --- | --- |
| React + TypeScript | 衣柜、属性面板、事件选择与页面交互 |
| Vite | 本地开发与构建 |
| PixiJS | 角色、服装和配饰的分层渲染 |
| Zustand | 当前穿搭、衣柜解锁和剧情状态 |
| 浏览器本地存储 | 带版本号的游戏存档 |
| 静态站点托管 | 发布首个可试玩版本，平台待定 |

React 负责界面，PixiJS 负责角色画面。游戏状态作为统一数据源，渲染层根据状态更新，不另行维护一套穿搭业务数据。

## 服装配置与状态设计

服装以数据配置接入，每件服装记录：

- 唯一 ID、名称、所属槽位及套装 ID。
- 纹理资源引用、图层顺序和定位信息。
- 属性加成、互斥标签和解锁条件。
- 必要时包含多个渲染部件，例如外套的前片与后片。

状态划分为服装目录、已解锁衣柜、当前穿搭、角色基础状态、剧情进度和日程阶段。当前穿搭只保存各槽位的服装 ID，不把整份服装配置复制进存档。

有效属性由基础状态、当前穿搭加成和事件效果统一推导。换装时重新计算服装贡献，避免多次穿脱造成数值重复累加。精神值等跨事件变化的状态通过明确的事件结算更新。

新增普通衣服以增加配置和素材为主；新增槽位或特殊玩法时，再扩展对应规则。配置校验覆盖重复 ID、非法槽位、缺失资源引用及不合法属性值。互斥搭配在应用前检查，向玩家说明冲突原因。

存档包含版本号，加载时执行校验与必要迁移。已删除或失效的服装 ID 回退到默认穿搭；损坏存档提供重置提示，避免页面无法进入。

## 美术与资源流程

计划先用 AI 生成角色和服装设计稿，再人工拆层、修正遮挡与边缘，并完成定位检查。生成稿不直接视为可用游戏素材。

1. 确定统一角色底模、姿势、画布尺寸和对齐基准。
2. 将服装拆成透明 PNG，检查与身体、头发、配饰的遮挡关系。
3. 对需要跨层遮挡的衣服拆分前后部件，配置各自图层。
4. 构建时打包成纹理图集与描述 JSON，保留原始尺寸和裁剪偏移，避免换装时位置跳动。
5. 按基础角色和服装包组织资源，避免新增内容后首屏一次加载全部素材。

首屏加载底模和默认套装，其他套装在浏览衣柜或选择时按需加载。资源齐备后一次性应用目标穿搭；快速连续选择时，只允许最新一次选择更新画面。加载失败则保留原穿搭，提示重试。

纹理缓存设置可调整的预算：保留当前画面使用的纹理，按引用情况释放闲置资源。共享图集仍被其他部件使用时不得提前释放。实际预算根据手机端测试结果确定。

## 剧情与内容扩展

事件配置包含事件 ID、触发阶段、触发条件、对白、可选行动、属性影响和后续事件引用。规则执行器统一处理条件判断与结算，避免把每个事件的判断散落在界面组件中。

首版先验证 5 个事件能够完成一轮游戏。后续优先扩充衣服、对白和事件配置；复杂规则确有需要时再增加能力。

## Devin Bot 协作计划

计划将 Devin Bot 用于持续处理明确的开发任务，形成“需求 → 实现 → 验证 → PR → 反馈”的协作流程。以下是目标工作流，尚未配置集成；触发方式以实际可用的账号权限和服务能力为准。

### 一次功能开发

以“新增雨天通勤套装”为例：

1. 我在 GitHub issue 中写清素材位置、穿搭规则、属性变化和验收条件。
2. 通过可用集成或手动派单交给 Bot，提供 issue 和仓库上下文。
3. Bot 阅读仓库约定，在独立分支补充配置、资源清单、实现和相关测试。
4. Bot 提交 PR，说明修改内容、验证结果、预览信息与待确认问题。
5. 我检查玩法和视觉效果，提出反馈；Bot 根据反馈继续修改。
6. 我确认验收结果并合并，随后发布试玩版本。

### 回归与故障处理

- 定时 CI 负责运行自动化回归；失败后，将日志、截图与复现信息交给 Bot 分析。
- Bot 在能够复现问题后定位原因、补充必要验证并提交修复 PR。
- 报错先去重，再关联已有 issue 或创建新任务，避免同一问题重复派单。
- 涉及玩法取舍、素材缺失或预算超限时，由我作出决定。
- 将项目约定、验收命令和常见故障记录在仓库中，供后续任务复用。

Slack 可作为计划中的派单与通知入口，GitHub issue 和 PR 保存任务事实与交付记录。浏览器自动化用于检查关键操作链路，手机实机体验另行验证；目前不承诺已接入真机测试服务。

## 首版验收标准

| 场景 | 预期结果 |
| --- | --- |
| 普通换装 | 对齐正确，遮挡关系正确，无明显闪烁 |
| 快速连续点击 | 最终显示最后一次选择的穿搭，旧请求不覆盖新结果 |
| 重复穿脱 | 属性计算一致，不重复叠加加成 |
| 互斥搭配 | 拒绝不合法组合并说明原因 |
| 断网或缺图 | 保留原穿搭，可重试，页面仍能操作 |
| 刷新页面 | 恢复穿搭、解锁状态与剧情进度 |
| 旧存档或失效服装 | 按迁移或回退规则恢复，不导致页面崩溃 |
| 事件循环 | 可完成从白天选装到夜间结算的一轮流程 |
| 手机浏览器 | 核心控件可点击，画面与文本适配屏幕 |

以上均为待实现和待验证的目标。实际完成情况将通过代码、测试结果、PR 和试玩版本逐步记录。
